== A. SCRIPT LINE TYPES (the runner: UFTGameInstance::TickExec, SRC\FTGameInstance.cpp:507-560; file loaded at FTGameInstance.cpp:109-120) ==
- Lines are trimmed; blank lines and lines starting with # are skipped (529). The first line runs no earlier than 4.0 s after game-instance Init (115). All waits are WALL-CLOCK seconds (FPlatformTime), not game time.
- `wait <seconds>` (531): pause that many real seconds. Must be "wait" + space.
- `waitfor <text>|<timeout s>` (536-544): continue when a captured log line CONTAINS <text> (case-insensitive substring), or after the timeout. The LAST '|' splits text from timeout; with no '|' the timeout is 30 s. The header comment's "waitfor <text> [s]" form (FTGameInstance.h:43) is wrong: a space-separated number becomes part of the text. A timeout does NOT stop the script; it logs `FT EXEC waitfor="<text>" result=timeout` (521) and goes on.
- `shot <name>` (545-550): FScreenshotRequest::RequestScreenshot(<SaveDir>/shots/<name>.png, bShowUI=true, no suffix), then 0.5 s pause. The HUD is in the frame. SaveDir = env WISPOS_APP_DATA if set, else <project>/Saved/FullThrottle (FTGameInstance.cpp:59-64). Same name twice overwrites.
- `quit` (551): FPlatformMisc::RequestExit(false). Exact word.
- Anything else is passed to GEngine->Exec(World, line) as a console command (553), then a 0.15 s pause (554). So the smallest step between two commands is 0.15 s, between two shots 0.5 s.
- Runner's own log lines: `FT EXEC file=<f> lines=<n>` (117), `FT EXEC cannot read <f>` (119, Error), `FT EXEC line=<n> cmd=<line>` (530; n counts every line of the file, 1-based), `FT EXEC waitfor="<t>" result=found|timeout` (521), `FT EXEC done` (557; if the script has no quit the game then runs on until the runner's budget).

== B. HARNESS COMMANDS (all in FTFlow.cpp HarnessCmd; every call logs `FT HARNESS <Cmd> <args>` at 895; in a world with no race game mode it logs Warning `FT HARNESS <Cmd>: no race GameMode in this world` at 1195 and does nothing) ==
Level numbers are 1-8 (game numbering) in every command. Kind names (KindArg, 864-876, case-insensitive): Biker, SnakeEyes or Hog, Rammer, SUV, Truck, Chopper, Boss, Civilian, Barrel.

Starting and driving
- `FTStartLevel <level=1> [scene=1] [sequel]` (1001 -> StartLevelAt 686-697): stops the attract mode, unpauses; if it is another level's map (or this map's track is a light attract build) it loads the map and starts the race, else it restarts the race on the spot (StartRace(false)). The game mode is new after a map load, so FTAutoRun/FTInvuln/FTHold/FTFreeze must be sent again after every FTStartLevel that loads a map.
- `FTAutoRun [wreck=<N|all|rest>] [leaveBehind=<N>] [wrapAt=<seconds|M:SS>] [turbo=<off|fullTanks|hold>] [level=<N>]` (1169-1184; effect at SRC\FTGameMode.cpp:1085-1095 and 1186): sets bAutoRun and bHarnessInvuln on THIS game mode, sets the game instance's bAutoDrive (the autopilot steers, for the rest of the session), holds SpeedUp. While bAutoRun the car never fires guns or missiles (1186), so wrecks come only from wreck= (each script vehicle that comes within 9000 cm ahead is wrecked until N are used; default 0) and the boss is not hurt. wrapAt kills a LIVE boss once the level clock passes that time (it does not summon one). Do not use level=: the flags are set on the old game mode and lost in the map load (only the autopilot survives, and it then shoots).
- `FTHold <SpeedUp|Turbo|Brake|Drift|Fire> [1|0]` (1088-1093): holds an input until released. Fire is ignored while FTAutoRun is active.
- `FTInvuln [1|0]` (1094): damage to the car becomes 0 and armor never drops below 1 (FTGameMode.cpp:1083, 1497).
- `FTKey <UE key name> [seconds=0.1]` (1161-1168): press, release after max(0.08, seconds) of GAME time through the world timer. e.g. `FTKey RightMouseButton 0.1` fires a missile.
- `FTNextScene` (1002-1007; Play phase only, not on the last scene): clears entities, jumps the car to the next scene.
- Console variables: `ft.Autopilot 1` (FTGameMode.cpp:43; autopilot drives, SHOOTS, and starts a race from the title after 1.5 s), `ft.AutoX <cm>` (45; the autopilot holds this road x, -1371..1371, -99999 = off: pins the lane), `ft.Hp <armor>` (46; start each race with this armor), `ft.Attract 0|1` (47; read when the title is entered), `ft.Shots <s>` (48; 1280x720 scene capture without HUD to <project>/Saved/Shots/ft_L<levelIndex>_<NNN>.png, FTGameMode.cpp:602-612, 4262).

SUMMONING: `FTBossNow` (FLOW:1008-1018)
- Works only in the Play phase; in any other phase it does nothing and only the invisible `FT HARNESS FTBossNow` line is logged. Confirm with `waitfor FT BOSS state=Arrive|10`.
- What it does: ClearEnts (everything on the road goes, including an earlier boss); marks the last scene's script spawns as done; moves the car to the finale distance (Def().FinaleD) keeping its lane and speed; SpawnGroup({Boss}) (GM:1667-1696): armor = the level's BossHp, first-attack timers T1=1.6 T2=1.0 T3=6.0, boss clock 0, escape time from the boss table; logs `FT BOSS state=Arrive armor=<hp> escape=<s> clock=0.0` and `FT BOSS firstAttack t1=1.6 t2=1.0 t3=6.0`. Then, for every level except game level 6, the boss is put straight on its fighting spot (State 0).
- Game level 6 THE ABOMINABLE keeps his real entrance (FLOW:1015-1016, GM:1676-1687, 2962-2999): he starts 2600 cm BEHIND the car, takes 4.5 s to come past (`FT BOSS yeti=alongside t=..`, then `FT BOSS yeti=turned ahead=..`), turns round in 0.7 s, and only then fights. His first charge logs `FT BOSS yeti=charge phase=<n>` (about 8 s after the turn).
- Calling FTBossNow again restarts the encounter from a fresh boss (full armor, timers and clock reset).
- Boss armor / escape seconds in SRC\FTData.cpp (lines 135, 173, 210, 245, 285, 318, 352, 385): L1 JUGGERNAUT 120/70, L2 ALCHEMIST 120/70, L3 BIG DEALER 200/90, L4 ENGINE 13 150/80, L5 MR. The escape time actually used comes from the progress data's boss table (GM:1691), which a spec file can override, so read `escape=` in the Arrive line rather than trusting these.

Result in order: `FT DAMAGE target=Boss ..`, `FT WRECK Boss cause=0 ..`, `FT BOSS state=Down clock=.. fight=.. lastChance=..` (GM:1977), finisher effect (`FT SHOP finisher=<id>` if one is equipped), `FT OUTCOME wrap clock=..` (GM:389), every other vehicle on the road is wrecked (GM:385-386), slow motion; 4.2 s later `FT RATING value=..`, the pay is saved (`FT SAVE slot=career_pie reason=Paycheck result=ok`), then `FT SCREEN name=Reel` if the run recorded any clips, otherwise `FT SCREEN name=Dailies` (GM:540-555). The reel ends with `FT SCREEN name=Reel state=hold`; `FTPress Continue` then gives `FT SCREEN name=Dailies`; again gives `FT SCREEN name=Paycheck lines=..`; again gives `FT SCREEN name=PreProduction next=L<n+1>` (after level 8: `next=Title`).
- `FTAutoRun wrapAt=<t>` does the same kill when the level clock passes t, but only if a boss is already alive (GM:1093-1094).

THE ESCAPE CLOCK (TickBossClock, FLOW:280-322): the boss clock runs at rate 1.0, slower (down to 0.5) when the car is faster than the boss's pace. At the escape time: `FT BOSS state=LastChance ..`, caption LAST CHANCE!, then within 8 s `FT BOSS state=Gone ..` and the level ends as got_away. So an unattended boss capture ends by itself roughly 70 to 95 s of game time after the Arrive line; plan the shots inside that or send FTBossNow again. `FTBossEscape` jumps straight to LAST CHANCE. A boss wrecked during LAST CHANCE gives the RUN DOWN stunt.

FTAutoRun exactly: see commands. In short it is "autopilot steers, car is invulnerable, car does not shoot, script decides the wrecks", and it must be sent again after each map load. The existing boss scripts (K:\Full Throttle\SkyScratch\SourceArt\Jam\unreal\fx_b1_bosses.txt) instead use FTInvuln 1 + FTBossNow + FTHold Fire 1 and were run with a different runner (fx_play.ps1) whose command line I did not read; under jam_exec nothing drives the car unless the script sends FTAutoRun or `ft.Autopilot 1` or -Extra "-ftauto".

HOW A NIGHT STARTS
1. Through the career (FLOW = FTFlow.cpp:372-383, FTNightFlow.cpp:38-53): on the Paycheck screen after a wrapped level, the real key path (`ft.Press Enter`, at least 0.6 s after `FT SCREEN name=Paycheck`) calls UFTNightFlow::GoToNight, logs `FT NIGHT start after=L<n> map=<map> next=L<n+1>` and opens the night map. `FTPress Continue` on the Paycheck does NOT (it goes straight to PRE-PRODUCTION). Not after level 8, not with -ftnonights. In a script run the day cutscenes are skipped unless -ftdays (FTNightFlow.cpp:102). When the night is won and its end card is passed, `FT NIGHT over next=L<m> preproduction on=<race map>` (FTNightFlow.cpp:78) and the race map opens on PRE-PRODUCTION.
2. Directly: the map as the first argument after the project (run_day1.sh). jam_exec.ps1 cannot do this through -Extra, because -Extra is appended after "-game ..." and the engine takes the start map only from the first argument. Inside a -ftexec script the console command `open /Game/Brawl/Maps/L_VelvetRoom` should do it (any console command is passed to the engine), but no existing script does this, so treat it as untested.

WHAT A SCRIPT CAN DO ON A NIGHT MAP
- The -ftexec runner lives in the game instance (DefaultEngine.ini: GameInstanceClass=/Script/FullThrottle.FTGameInstance), so it keeps running on night maps: `wait`, `shot <name>` (with HUD, into the same shots folder), `quit`, console variables `ftb.Auto` and `ftb.Win`, and `ft.Press <Key>` all work.
- Every FT* command only logs `FT HARNESS <cmd>: no race GameMode in this world` there.
- waitfor is nearly blind: all the brawl's lines start "FTBRAWL" and are not captured. Usable texts are `map=L_RustyAnchor` etc. (the `FT MUTE reapplied muted=.. map=..` line after the map load), `FT WARM brawl done`, `FT NIGHT start`, `FT NIGHT over`. Everything inside a fight has to be timed with `wait`.
- Keys (BGM:417-442): A/D or Left/Right walk, W/S or Up/Down change lane, J or Z punch, K or X kick, SpaceBar jump, L or C grab, Enter = next / retry. ft.Press is a 0.12 s tap, enough for a punch or Enter, not for walking. In cutscenes any of punch/kick/jump/Enter hurries a line, Tab skips the cutscene, end cards wait for Enter (FTBrawlCutscene.cpp:551-631).

FTBRAWL LOG LINES FOR CHECKS AFTERWARDS (log file only): `FTBRAWL start <VENUE> night=<n> waves=<w> wave=<k>` BGM:280; `FTBRAWL wave <i>/<n> locked at x=..: <k> foes` 396; `FTBRAWL wave cleared -> <n> (kos=..)` 1083; `FTBRAWL boss <NAME>` 407 (the boss walks in; 2.2 s intro); boss moves: `boss slam` 935, `boss whirlwind` 874, `boss dizzy` 881, `boss revolver lane=..` 902, `boss fire breath lane=..` 1106, `boss strike lanes=..` 1127, `boss bear hug lunge|caught|broken|throw` 1157-1188, `boss anchor sweep` 1201, `boss calls 3 more` 969; `FTBRAWL won kos=.. best=.. hits=.. time=..` 783; `FTBRAWL retry wave <n>` 1253; cutscenes `FTBRAWL cut <id> line ..`, `FTBRAWL cut end <id>`, `FTBRAWL fight begins x=.. y=..` (FTBrawlCutscene.cpp:522, 538, 547); `FTBRAWL on to the next race|day <n>|night <n>` 1261-1270.

DETERMINISM: the fight runs in fixed 1/60 s steps (BGM:51, 1323-1325) on its own seeded random stream (Rnd.Initialize(1986 + a per-night seed), BGM:181, 218, 234, 240), and the autopilot's choices are a function of the fight state, so the same build should replay the same fight in fight time. Wall-clock waits and -brawlshotdt still drift with hitches, and the overhaul may change timings, so pair frames on events you can see in the log afterwards rather than on exact seconds.

==================== CAUTIONS
SRC = K:\Full Throttle\UE\full-throttle-unreal\Source\FullThrottle. All from reading the code; none of it was run, and items marked "untested" are my reading of engine behaviour.

waitfor
1. It sees only lines starting "FT " and never "FT EXEC"/"FT HARNESS" lines (FTGameInstance.cpp:493, 518). FTBRAWL, FTTRACK, FTDRESS, FTMUSIC, FTQUALITY, FTHITCH lines cannot be waited on.
2. The search window starts at the last console command, not at the waitfor (552). Two waitfors in a row for the same text both match the same old line. To wait for a NEW occurrence put any harmless console command between them (e.g. FTDumpLevel).
3. Because of 2, after `FTStartLevel` from the title a `waitfor FT SPEED` can be satisfied by a stale line: the attract demo behind the title is still in the Play phase for a frame or two before the map load. The existing fx scripts have this (FTStartLevel, waitfor FT LEVEL id=, waitfor FT SPEED). Safe order: FTStartLevel N; waitfor FT LEVEL id=|240; then a console command (FTAutoRun.. or FTInvuln 1); then waitfor FT SPEED|60.
4. `FT CLOCK level=8.0` can be missed: the value is printed with one decimal at the first frame past the second, so a frame longer than 50 ms prints 8.1 and the waitfor runs to its timeout (jam_verify/jam_play use the .0 form). Wait for `FT CLOCK level=8.` instead (still unique: 18. does not contain it).
5. `FT BOSS clock=<x>` values are not on round numbers (a static 0.5 s accumulator, FTFlow.cpp:286-293); do not wait for an exact boss-clock value.
6. A timeout does not stop the script. The following shots are then taken at the wrong moment. After each run grep the log for `result=timeout`.
7. Default timeout is 30 s if the `|seconds` is left off; a map load on this disk needs 200-240 s.

Phases
8. FTBossNow, FTWrapNow, FTNextScene and FTCrash do nothing outside the Play phase, silently. After `FT LEVEL id=` the slate (Card phase) lasts 3.2 s (FTGameMode.cpp:513), longer in wall-clock if frames hitch. Wait for FT SPEED or FT CLOCK first, and confirm FTBossNow with `waitfor FT BOSS state=Arrive|10`.
9. FTFreeze only acts in the Play/Wreck/Wrap phases, and it is not cleared by a restart on the same map; always send `FTFreeze 0`.
10. A new map = a new game mode: FTAutoRun, FTInvuln, FTHold, FTFreeze are gone after any FTStartLevel that loads a map. The autopilot flag (set by FTAutoRun or -ftauto) is NOT gone: it stays for the session, and without FTAutoRun it shoots.
11. Once the autopilot flag is on, the title starts a race by itself after 3.5 s (FTGameMode.cpp:693). Photograph menus before the first FTAutoRun, or in their own launch.
12. `ft.Press Escape` on the title quits the game (FTGameMode.cpp:690, 713).

Determinism
13. All waits are wall-clock; the game runs on game time. Hitches (first-use shaders, loads, other Unreal jobs on the PC) and the game's own slow motion after spectacular wrecks shift what a fixed `wait` lands on. For a single still use FTSlowMo then FTFreeze 1 / shot / FTFreeze 0 (as fx_c_blasts.txt does); for sequences accept that frames pair by moment, not pixel.
14. Random, different every run: the lane of FTSpawn (FTFlow.cpp:898), pickup drops, several boss choices (e.g. FTGameMode.cpp:2709, 2735, 2797), the attract shot behind the title. Boss attacks aim at the car's x, so pin it: `ft.AutoX <cm>` with the autopilot driving. The engine switch -fixedseed may steady the first random draws; untested here.
15. The title is not comparable with the attract demo running (random level position, random damage, a map load every 11 s that can collide with the script's first commands). Use jam_exec -Extra "-ftnoattract". Then nothing prints FT SPEED on the title, so do not copy the fx scripts' opening `waitfor FT SPEED|200`.
16. Quality: send `FTQuality 3` (or the level wanted) first; without it the preset comes from each checkout's own settings.json or the AUTO benchmark. Dynamic resolution is on by default and changes sharpness with GPU load: add -ftnodynres to -Extra on both runs.
17. jam_exec does not set WISPOS_APP_DATA, so each checkout uses its own Saved\FullThrottle. Start every script with FTUseTestSlot then FTCareerReset so the real career is untouched and both runs start equal. settings.json is still shared with the checkout and differs between the two checkouts: best takes shown on the title, FPS counter, reduced motion, key layout. These write it: a wrapped level with a new best score (FTGameMode.cpp:421-425), FTSetBest, Left/Right in Options, a rebinding in Controls, the M and F1 keys. Title and options frames can therefore differ for reasons that are not the overhaul.
18. jam_exec does not clear K:\Full Throttle\SkyScratch\HandBack\jam\play\<Tag>; use a new tag per run or old frames stay beside the new ones. Shot names are the pairing key: fixed names, no counters that depend on timing.
19. Frame size must be the same on both runs (default 3440x1440, -Small 1720x720).

Commands that bite
20. `FTWreck all` kills the boss too and ends the level.
21. `FTHold Fire 1` does nothing while FTAutoRun is active; FTCrash does nothing while FTInvuln or FTAutoRun is on.
22. `FTPress Continue` is ignored on the reel until `FT SCREEN name=Reel state=hold`; and from the Paycheck it bypasses the night.
23. FTAutoRun level=N loses its own flags in the map load; use FTStartLevel, the waitfor, then FTAutoRun.
24. `FTSpawn Boss` makes a boss without the encounter set-up; use FTBossNow.
25. A boss escapes by himself after his escape time (70-95 s of game time), which ends the level as got_away with no reel.
26. FTKey releases on game time, so under FTSlowMo/FTFreeze the key stays down much longer. ft.Press releases through a world timer too; while the pause menu is open that timer probably does not run (untested), so repeated presses of one key in the pause menu may not register.
27. ft.Click uses viewport pixels and a real cursor; with -RenderOffScreen and two frame sizes it is not dependable.
28. On night maps every FT* command is a no-op with a warning; only wait, shot, quit, ft.Press, ftb.Auto, ftb.Win work, and the brawl flags (-brawlwave etc.) are per process, not per map.
29. End every script with `wait 1` then `quit`. Without quit the game runs until jam_exec's budget, which then prints "TIMEOUT ... left running"; no other game may be started until that process has ended.
30. Track-build variables (ft.Dress, ft.Land, ft.Ads, ft.DressBank ..., FTTrack.cpp:19, 150-160) are read when a level's track is built: set them before FTStartLevel or with -dpcvars, not after.

Things I was asked to read that are not what the brief says
31. The FT* commands are in FTFlow.cpp, not FTPlayerController/FTGameMode (those hold ft.Press/ft.Click and the ft.* variables).
32. boss_polish.ps1 is an art tool, not a runner (see brawl_notes). No Brawl runner for Windows exists in the places named.
33. The fx_*.txt scripts name fx_play.ps1 as their runner in their headers; I did not read it, and they assume something is already driving the car.
